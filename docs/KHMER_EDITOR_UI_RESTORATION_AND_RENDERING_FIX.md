## 1. Executive Summary

The user experienced two major issues during Khmer PDF editing:
1. **Unwanted UI changes:** A floating toolbar (`KhmerOSMuol`, `+128px`, `Done`, `Close`) was introduced over the canvas. The user explicitly disliked this floating interface and requested the restoration of the canonical 3-panel layout (canvas in center with interactive hitbox outlines, and all editing controls in the right-side Properties panel).
2. **Khmer text corruption & visual distortion:** When existing text was edited, the text on screen appeared distorted, squished, overlapping, unnaturally bold, and surrounded by an opaque white rectangle that blocked surrounding text. Additionally, exporting documents with Khmer filenames caused a `UnicodeEncodeError` in HTTP `Content-Disposition` headers returning HTTP 500 (`Docera could not complete this request. Please try again.`).

Both issues have been completely resolved:
- The floating toolbar and floating textarea have been removed entirely.
- The canonical 3-panel workflow has been restored: clicking any text span highlights it on canvas with a crisp outline and opens the editing controls in the Right-side Properties panel.
- The double-rendering defect (drawing an HTML overlay over canvas vector glyphs) has been eradicated. The canvas renders the authoritative in-memory PDF generated by the backend PyMuPDF + HarfBuzz engine.
- HTTP `Content-Disposition` headers are RFC 5987 / RFC 6266 compliant with ASCII fallback, completely eliminating the 500 error on Khmer exports.

## 2. Confirmed Root Causes

### Root Cause 1: Duplicate HTML Text Overlay & White Occlusion Box
Previously, the editor attempted to preview edits by injecting an HTML `<div>` (`.existing-text-replacement`) inside an opaque white box (`background-color: #ffffff`) directly over the PDF canvas:
- The replacement `<div>` was constrained to the original span's bounding box height (~12px) with `line-height: normal`.
- Browser HTML text rendering cannot match OpenType HarfBuzz vector advances for complex scripts (such as Khmer subscript consonants / coengs like `ក្ក`, `ញ្ជ`, `ប្ដ` and upper/lower vowels `ិ`, `ុ`).
- Because the backend authoritative preview was *also* rendering vector glyphs on the canvas below, the HTML text was rendered directly on top of the vector glyphs with slight sub-pixel offsets. This caused the text to appear unnaturally bold, blurry, and overlapping, while the white background blocked surrounding lines.

### Root Cause 2: Unwanted Floating Inline Toolbar
An inline floating editor component (`ComplexScriptInlineEditor.tsx`) was rendered on top of the canvas, adding floating pills, dropdowns, and buttons that cluttered the document workspace. The user requested the original, clean 3-panel Properties panel workflow.

### Root Cause 3: Non-ASCII Characters in HTTP Headers (`UnicodeEncodeError`)
When exporting modified documents, `_binary_response` passed raw Khmer strings in the `Content-Disposition` header:
```python
# Before (Caused HTTP 500 error):
headers["Content-Disposition"] = f'attachment; filename="{filename}"'
```
According to ASGI and RFC 7230 standards, HTTP headers must be ISO-8859-1 (Latin-1). Starlette attempted `header_value.encode('latin-1')`, which threw `UnicodeEncodeError: 'latin-1' codec can't encode characters in position 22-31`. This resulted in the user-visible error: `Docera could not complete this request. Please try again.`

## 3. Architecture & Implementation Changes

### Objective A: Restored Canonical 3-Panel Properties Workflow
- **Deleted `frontend/src/features/editor/ComplexScriptInlineEditor.tsx`**: Removed all floating on-canvas UI, toolbar buttons, and floating inputs.
- **Removed Obsolete CSS**: Purged `.complex-script-inline-wrapper`, `.inline-editor-toolbar`, `.inline-editor-font-pill`, `.inline-clean-khmer-btn`, `.inline-overflow-badge`, `.inline-btn`, `.complex-script-textarea`, `.existing-text-replacement`, and `.existing-text-inline-input`.
- **Restored Properties Panel Controls**:
  - Clicking any text span on the canvas sets `selectedSpan` and focuses `replacementInputRef` in the right-side Properties panel.
  - The Properties panel provides:
    - **Original text**: Read-only display of the extracted text.
    - **Replacement text**: Multiline textarea styled with the resolved font (`line-height: 1.6`, generous padding, smooth typography).
    - **Clean Legacy Khmer Unicode**: Automatically surfaces when Limon/ABC keyboard encoding artifacts are detected (e.g. `ដផ្អកគលើ` $\to$ `ផ្អែកលើ`, `គតើ` $\to$ `តើ`, `គនេះ` $\to$ `នេះ`, `គោក` $\to$ `លោក`, `ឆ្្ុំ` $\to$ `ឆ្នាំ`).
    - **Font family selector**: Allows selecting Detected font, full KhmerOS family (Battambang, Muol, Content, Bokor, Metal Chrieng), Noto Serif/Sans Khmer, or Latin fonts.
    - **Font size & color picker**.
    - **"Apply text change"** (`Ctrl+Enter` shortcut) and **"Revert"** buttons.

### Objective B: Canvas Hitbox & Authoritative Vector Preview
- The `.existing-text-span` element on the canvas is now strictly an invisible/translucent interactive hitbox:
  ```css
  .existing-text-span {
    position: absolute;
    box-sizing: border-box;
    cursor: pointer;
    background-color: transparent;
    transition: outline-color 0.15s ease, background-color 0.15s ease;
    border-radius: 2px;
  }
  .existing-text-span:hover {
    outline: 1.5px dashed rgba(35, 102, 90, 0.6);
    background-color: rgba(35, 102, 90, 0.04);
  }
  .existing-text-span.selected {
    outline: 2px solid var(--forest) !important;
    background-color: rgba(35, 102, 90, 0.12) !important;
  }
  .existing-text-span.edited {
    outline: 1.5px dashed var(--forest);
    background-color: transparent;
  }
  ```
- **Zero HTML Text Overlay**: All visual rendering of modified text is performed directly on `<canvas>` by PDF.js loading the backend-generated authoritative in-memory PDF.
- **HarfBuzz Complex-Script Shaping**: The backend uses HarfBuzz with full GSUB/GPOS OpenType tables, ensuring 100% correct glyph shaping, vowel placement, subscript consonant stacks, and Adobe-Identity-UCS ToUnicode CMaps for searchability.

### Objective C: RFC 5987 / RFC 6266 Unicode Header Encoding
Fixed `_build_content_disposition()` in `backend/app/api/tools_routes.py`:
```python
def _build_content_disposition(filename: str) -> str:
    clean_name = re.sub(r"[\r\n\t]+", " ", filename).strip() or "document.pdf"
    ascii_clean = re.sub(r"[^\x20-\x7E]", "", clean_name).replace('"', "").replace("\\", "").replace(";", "").strip()
    if not ascii_clean:
        ascii_clean = "document-edited.pdf" if clean_name.lower().endswith(".pdf") else "document"
    elif clean_name.lower().endswith(".pdf") and not ascii_clean.lower().endswith(".pdf"):
        ascii_clean = f"{ascii_clean}.pdf"
    encoded = urllib.parse.quote(clean_name, safe="")
    return f'attachment; filename="{ascii_clean}"; filename*=UTF-8\'\'{encoded}'
```
Both the browser and PDF tools receive the correct filename without triggering ASGI header encoding errors.
